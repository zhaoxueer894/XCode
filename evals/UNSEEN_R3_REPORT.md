## 核心发现:委派几乎没发生

**10 道题里 7 道 delegate 调用次数为零**——编排者(deepseek-flash)在工具开放的情况下几乎总是自己做完,只有 3 道 dayjs 真正委派(1-3 次)。因此**本轮不构成多智能体与单智能体的对照**:8 道公平判定里 7 道事实上仍是单智能体运行。真正的多智能体运行只有 3 道 dayjs:1 通过 2 未通过。

多智能体设计在真实仓库上的验证结论是:**当前状态下,"开放委派"不等于"使用委派"**。编排者不委派的可能原因:delegate 工具说明不够有说服力、任务提示词没有任何引导、deepseek-flash 的行为倾向。这是多智能体路线的下一个待解决问题——在 30 题对照之前,需要让委派真实发生(任务提示引导,或强制规划-实现-复查的流程),否则对照实验测不到要测的东西。

与轮 2(5/6,不同题集)的表观差异**不归因于多智能体**:7/8 事实单智能体,题集难度也不同。cli 仓库 2/3 通过(此前 6 道全败)同样发生在零委派运行里,与门禁机制一致而非委派的功劳。

## 过程中根治的两个问题

1. **capture 脚本在 Python 3.6 testbed 上无法解析**(django 10880/10914 补丁丢失,即轮 2 django-9296 的追溯根因):`from __future__ import annotations` 与 PEP 604 注解需要 3.7+/3.10+,老 django conda 环境是 3.6。已去除全部注解保证任意 Python 3 可解析(`c5039b5`)。两道题模型已见过,不重跑,计基础设施失败。
2. **一条流式工具调用的参数 JSON 非法会杀死整个请求**(sympy 13031 第 6 步,26k token 报废):现在只丢弃该条调用、保留其余,模型看不到结果会自行重试——与门禁的响应级剪除同语义;仅全部调用报废且无正文时才报错(`57ccbfa`)。

三个修复(capture 3.6 兼容、流式容错、此前的响应剪除)都有回归测试;CI 双平台绿。
